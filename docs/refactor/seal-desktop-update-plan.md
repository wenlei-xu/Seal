# Seal 桌面更新方案

本页保留 2026-10-08 根据当前源码与 Magpie 官方更新实现提出的方案。现已按 GitHub Releases 方式接入 Seal 仓库，已完成的范围和保留事项见 seal-desktop-update-implementation.md。下方“待补”表描述设计时的缺口，不能代替当前状态。Magpie 的核实记录见同目录 magpie-update-research.md。

## 用户体验

1. 启动后延迟检查，运行中定期检查；设置提供手动检查和自动下载开关。
2. 有新版本时在后台下载与验证，显示版本说明、进度和大小，用户继续工作。
3. 下载完成后提示“保存并重启更新”与“稍后”。首版不默认在用户退出时自动安装。
4. 剪辑导出、本地转写、Agent 制作等任务未结束时，默认等待，不中断工作。
5. 保存与任务检查通过后停止旧运行端，由独立更新助手替换完整程序资源，再启动新版本。
6. 明确显示失败原因，保留可恢复的旧程序。已迁移的数据不能仅通过换回旧 EXE 恢复。

## 发布流程

提交固定版本 → 自动构建完整包 → 包完整性检查 → 自己验收候选包 → 确认发布 → 更新公开版本清单。

稳定版需要明确确认，不因每次普通提交直接发布。后续可增加用户主动选择的测试通道；当前稳定版本解析和清单不能直接冒充已支持 prerelease 通道。

每个版本的包保持不可变。切换最新版只改变版本清单。用户可以直接更新到最新版，但数据库迁移必须覆盖中间步骤。

首版可以使用自己的 GitHub Releases 存放包及签名清单。根据实际下载表现增加自己的静态下载站或对象存储镜像；镜像包仍需通过同一签名清单和哈希验证。版本检查服务只提供公开元数据，不接收用户工程或模型凭据。

## 频繁更新时的体积控制

程序与固定大型依赖分目录规划：前端、Go 后端、Agent/剪辑运行逻辑随兼容版本一起更新；浏览器、Node、FFmpeg、ASR 模型按固定版本或摘要复用。是否拆包以正式包体积和维护成本为依据。

如果实现依赖独立下载，签名清单必须指定精确版本、大小、摘要和兼容约束。所有新依赖准备好并校验通过后才切换程序版本。不能让运行端自行追踪 latest，也不能把部分更新成功的混合版本标为就绪。

内置 Skill 与相应运行端的版本保持匹配。用户安装、创建的 Skill 及其启停状态、工程、素材、API Key 不属于安装目录替换范围。

这里的依赖复用与二进制差分是两种能力。首版不承诺差分下载、运行中热替换或不停机更新。

## 首发必须提前确定

- 自己的发布仓库与公开 HTTPS 清单、下载地址。
- 自己的更新签名密钥；客户端仅带公钥，私钥只用于受控发布。
- 首发平台与正式版本编号；前后端、包清单的版本一致。
- 首发安装包已带更新配置。当前关闭更新的开发预览需手动安装一次正式版本。

## 最小升级验收

使用实际打包文件验证旧版到新版的检查、下载、保存、替换、启动和剪辑导出。额外覆盖下载中断、文件占用、活跃任务、替换失败与迁移失败；不把进程成功启动当作工程能使用的证明。
